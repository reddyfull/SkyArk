## 2024-05-13 - [Optimize Where-Object Pipeline in String Counting]
**Learning:** Using `$string | Where-Object {$_ -eq ','} | Measure-Object` treats the string as a 1-item array and checks if the ENTIRE string is equal to `,` or matches `*-Thr*`. It always returns 0 because the string length > 1, so the condition fails. The original code in `AWStealth.ps1` lines 1050-1051 contains a logic bug where it attempts to count occurrences of `,` and `-Through*` within the string `$_.PolicyName` but effectively always counts 0.
To fix the logic AND optimize it, using regex matching like `[regex]::Matches($var, 'pattern').Count` or `.Split(',').Count` or `String.Length - String.Replace(',','').Length` is faster and correctly identifies substring occurrences. Alternatively, based on memory conventions, native array casting with operators `@(@($var.Split(',')) -like '*-Thr*').Count` is optimal and handles the `$null` and scalar cases correctly.
**Action:** Replace pipelines doing string filtering with string manipulation/regex or array casting native operators to preserve logic correctly and bypass pipeline overhead.
## 2024-05-13 - [AWStealth String Pipeline Counting Optimization]
**Learning:** Found an O(N) array filtering logic bug where strings were implicitly piped through `Where-Object` array matching (`| Where-Object {$_ -eq ','} | Measure-Object`). For a string variable like `$_PolicyName`, this evaluates the whole string, never finding individual occurrences of `,` or `-Thr*`.
**Action:** Replace `Where-Object | Measure-Object` with `[regex]::Matches($var, 'pattern').Count` or `@(@($var.Split(',')) -like '*-Thr*').Count` for correct substring/array element counting. This fixes the bug and reduces performance overhead from 608ms to 200ms per 1k loops.

## 2024-05-13 - [AWStealth Regex Null Handling Regression]
**Learning:** Replacing pipeline counting with `[regex]::Matches($var, 'pattern').Count` can throw a `MethodInvocationException: Value cannot be null` exception if `$var` is `$null`. However, casting the variable to a string via `[string]$var` safely handles `$null` and produces an empty string. The original regex implementation caused a regression in potential null handling, although testing showed `$null` is handled gracefully without `Set-StrictMode`, it's safer to explicitly cast.
**Action:** Always cast the input variable to `[string]` (e.g., `[string]$_.PolicyName`) when using static `[regex]::Matches` on object properties to avoid potential runtime crash regressions.
