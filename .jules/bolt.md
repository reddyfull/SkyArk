## 2024-05-19 - Replace pipeline overhead with native properties for primitive and collection counting
**Learning:** Found significant pipeline overhead where `Measure-Object` was used on scalar and array values instead of the native `.Count` property. This approach not only introduced massive overhead on small checks inside heavy parsing loops, but also led to critical logic bugs. For instance, piping a single string through `Where-Object {$_ -eq ','} | Measure-Object` evaluates the entire string as a 1-item object instead of char-by-char, yielding `0`. Similarly, `($var | Measure-Object).Count` absorbs `$null` safely but `.Count` alone throws a fatal error if the variable hasn't been instantiated as an array/list.
**Action:** When filtering or counting elements to avoid loop bottlenecks, use `$var.Count` safely if `$var` is guaranteed to be initialized or an array. To avoid `$null` execution bugs and the pipeline performance tax, force the expression into an array block `@( ... )` and apply native matching (`-like`, `-match`, `-eq`) directly. For strings, replacing `Where-Object` with `-split` (`[string]$str -split ','`) prevents pipeline false-negatives while staying null-safe and heavily outperforming `.Split()`.
