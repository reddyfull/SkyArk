## 2024-05-18 - [PowerShell Pipeline Overhead]
**Learning:** Using `| Where-Object | Measure-Object` inside a tight loop causes a massive performance bottleneck due to pipeline overhead (e.g., 1800ms vs 73ms for 1000 iterations). Additionally, when splitting strings to count elements, one must handle `$null` values safely since method calls like `.Split()` throw runtime errors on `$null`, unlike the pipeline which safely ignores them.
**Action:** When counting substrings or filtering array elements inside a loop, avoid `Measure-Object`. Instead, use string methods like `.Split().Count - 1` with a null check (e.g., `if ([string]::IsNullOrEmpty($val)) { 0 } else { ... }`), or native array operators like `@(@(...).Split(',')) -like 'pattern').Count` which safely handle nulls and arrays while avoiding pipeline overhead.

## 2024-05-18 - [PowerShell Array Filtering Optimization]
**Learning:** Using `| Where-Object | Measure-Object` inside a loop causes a massive performance bottleneck due to pipeline overhead (e.g., 2300ms vs 80-400ms for 1000 iterations depending on the approach). Replacing this with string `Split` causes runtime errors on `$null` or array inputs and breaks original pipeline semantics where strings are evaluated as arrays of 1 item, rather than character arrays.
**Action:** When filtering array elements or counting specific elements in a scalar/array variable inside a loop, avoid `Measure-Object` and `Where-Object`. Instead, use native array operators (e.g., `@(@($var) -eq ',').Count` or `@(@($var) -like '*-Thr*').Count`) to safely handle nulls, scalars, and arrays while preserving semantics and avoiding pipeline overhead. Replace `+=` array concatenations inside loops with `System.Collections.Generic.List[T]`.
